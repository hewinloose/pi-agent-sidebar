## 目标

在 pi-agent-sidebar 中实现六项功能，参考 `D:\code\PI-Desktop` 的实现思路：

1. 思考过程可折叠，默认展开，**回复完成后自动折叠**
2. 删除用户消息时连带其后回复一起删除
3. 从某条回复新建分支
4. 编辑用户消息
5. 重新生成回复
6. 子代理运行显示已用时长；主代理可自行掐断

---

## 一、关键事实（决定了方案形态）

| 事实 | 结论 |
|---|---|
| pi RPC 有 `fork`（只能从**用户消息**分叉）、`switch_session`、`get_fork_messages`、`get_entries` | 分支可直接用；删除/编辑/重生成**无原生 API** |
| pi 的 `ctx.sessionManager` 对扩展**只读**，扩展 API 无删除入口 | 无法借助扩展实现 |
| 会话文件格式是**公开文档**（JSONL v3，`id`/`parentId` 追加式树） | 可安全重建，但需版本守卫 |
| `PiState.sessionFile` 已存在；`switch_session` + `waitForSessionReplacement` 已在用 | 重建后重载的链路现成 |
| 现有 `deleteProjectSession` 只删整个文件；快照来自 `get_messages`（窗口 600），**不含 entryId** | 需新增「用户消息序号 → entryId」解析 |

**已定决策**：需求 2/4/5 走 **B 路线**（会话文件重建）。不原地改写，而是**拼出一个修正过的新会话文件，用官方 `switch_session` 加载，原文件完全不动**（切回即撤销）。

**需求 6 的现实**：`trellis_subagent` 是阻塞工具，pi 的 `abort` 只是「发信号并等会话空闲」，不会抢占。所以主代理要「掐断」，唯一可行形态是工具接受一个**由主代理自己决定的上限**（`timeoutSeconds`），到点由工具杀子进程并返回已完成的部分。产品侧不写死任何策略。

**需求 1 的判定标准**（此需求有歧义，采用字面义）：所有思考块**默认展开**；只有**在视图中实时流式完成**的那条消息会在完成瞬间被自动折叠一次；用户手动展开/折叠的显式选择永远优先，且不会被自动折叠覆盖。

## 三、分阶段实施

### Phase 1 — 思考块折叠（纯 webview，无协议改动）

- `webview/transcript/controller.ts`
  - 把 `expandedThinkingKeys: Set` 改为两个集合：`thinkingChoices: Map<key, boolean>`（**仅**记录用户显式选择）与 `autoCollapsedKeys: Set<key>`（自动折叠标记）。
  - 有效展开 = `thinkingChoices.get(key) ?? !autoCollapsedKeys.has(key)`。
  - `settle()`（现位于 `controller.ts:149`，由 `message_end` 触发）里，把**正在流式的消息**的思考 key 加入 `autoCollapsedKeys`；`agent_settled` 兜底（见 `rpcEventReducer.ts:60`）。
  - `setThinkingVisibility()` 改为写 `thinkingChoices`；`pruneThinking()` 同步清理两个集合；会话切换时清空。
- `webview/transcript/renderer.ts`（`thinkingBlockHtml` 约 717 行，展开位 561 行）
  - 由「默认折叠」改为「默认展开，除非 `autoCollapsed` 或显式 false」。
  - 渲染签名必须包含**解析后的展开态**，保证切换只重建该消息节点（沿用现有 `tk…` 签名机制，`controller.ts:204`）。
- `webview/styles/transcript.css`：反转 `.thinking-block` 的显隐规则（975-981 行附近）；折叠动画与 `is-expanded` 解耦。
- 滚动补偿复用现有 `restoreThinkingAnchor`（`controller.ts:244`），不改。
- 测试：`test/unit/webview/thinking-groups.test.mjs`、`transcript-sections.test.mjs`、`transcript-controller.test.mjs` 增补「默认展开 / settle 后折叠 / 显式选择优先」。

### Phase 2 — 工具卡已用时长（纯 webview）

- 新建 `webview/transcript/toolDuration.ts`：`formatElapsed(ms)`（`12s` / `1m 05s` / `1h 02m`），纯函数便于单测。
- `webview/transcript/renderer.ts`
  - `toolHeaderParts()`（847 行附近）在 `.header-trail` 内、`.tool-hint` 之前插入 `<span class="tool-elapsed" data-started-at="<epoch>">`。
  - 仅当 `resolveToolStatus() === "running"` 且 `live.startedAt > 0` 时输出（历史/合成工具 `startedAt` 为 0，见 `rpcEventReducer.ts:194` 与 bash 合成工具）。
  - **不进入**渲染签名与分区缓存，避免每秒重建节点。
- `webview/main.ts`：把现有 1 秒相对时间 ticker（`refreshRelativeTimes`，1319-1356 行）扩展为同时刷新 `[data-started-at]` 的 textContent；仅当存在运行中工具时才启动。
- `webview/styles/transcript.css`：`.tool-elapsed` 样式，沿用 `--pi-muted`，等宽数字。
- 该实现对**任意**工具生效，`trellis_subagent` 自然覆盖，不写特例。
- 测试：`toolDuration` 单测 + `region-renderers.test.mjs` 断言运行中出现、结束后消失。

### Phase 3 — 每消息操作栏 + 协议（后续阶段的地基）

- `shared/protocol.ts` 新增 4 个 Webview→Host 消息（沿用 `deleteSession` 的形状与 `actionId` 约定）：
  ```
  { type: "deletePrompt";     actionId; promptOrdinal; text }
  { type: "editPrompt";       actionId; promptOrdinal; text; newText }
  { type: "regeneratePrompt"; actionId; promptOrdinal; text }
  { type: "forkPrompt";       actionId; promptOrdinal; text }
  ```
  边界：`text`/`newText` 用 `MAX_MESSAGE_LENGTH`，`promptOrdinal` 用 `nonNegativeInteger`。
- `shared/protocolParser.ts`：4 个分支（无效输入返回 `undefined`）；`WEBVIEW_REQUEST_TYPES` 增补（`tsc` 覆盖断言强制）。
- `webview/transcript/renderer.ts`：新增 `messageActionsHtml()`，输出
  `data-message-action="delete|edit|regenerate|fork"` + `data-message-key`；用户消息出 edit/delete，助手消息出 regenerate/fork；流式中或忙时不出。
- `webview/main.ts`：复用 `#messages` 上已有的两个委托监听（click 796 行 / keydown 873 行），走现有 `runAction` 拿 `actionResult`；删除用 `ModalController` 二次确认（PI-Desktop 也是确认后再改）。
- `src/provider/webviewMessageRouter.ts`：4 个 `case` + 选项；`src/provider/piViewProvider.ts`：实现回调并统一走 `enqueueSessionMutation({ requireIdle: true })`。
- 测试：`test/unit/shared/protocol.test.mjs` 自动覆盖新变体；`host-message-handler` 相关测试同步。

### Phase 4 — 从回复新建分支（复用现有 fork）

- host 侧新增解析：`resolvePromptEntryId(ordinal, text)` —— 用**已有的** `get_fork_messages`（`piViewProvider.ts:863`）取 `{entryId, text}` 列表，按序号取候选并**校验文本**；不匹配则返回明确错误（例如窗口截断导致列表与视图错位），并禁用操作，绝不猜测。
- `forkPrompt` 解析出 entryId 后直接复用现有 `forkSession(entryId)`（888 行，含 entryId 再校验 + `waitForSessionReplacement`）。
- fork 成功后把 pi 返回的 `data.text` 回填到输入框（`setComposerText` 已有通道），便于立即改写再提交。

### Phase 5 — 删除 / 编辑 / 重新生成（会话文件重建）

**新增 `src/services/sessionHistory.ts`（`/// <reference types="node" />`，不依赖 vscode）**

纯函数 + 一个写盘函数：

```ts
interface SessionDocument { header; entries; byId }
readSessionDocument(contents: string): SessionDocument      // 校验：header.type==="session"、version===3、每个 entry 有 id/parentId
activeBranch(doc, leafId): Entry[]                          // 从 leaf 沿 parentId 回溯
planDeletePrompt(doc, entryId): Plan                        // 删该用户条目 + 其后直到"下一个用户条目(不含)"，并把后继条目重挂到被删区间的父节点
planTruncateFromPrompt(doc, entryId): Plan                  // 删该用户条目及其后全部（编辑/重生用）
applyEditText(plan, entryId, newText): Plan                 // 替换该用户条目的文本
serializeSession(plan): string                              // 原 id 保留；父链在拼接点重连
```

- 所有 `plan*` 为纯函数 → 可直接用 fixture JSONL 单测，无需文件系统。
- 写盘是**新建文件**：同目录、同命名规则（`<ISO 时间戳>_<新 uuid>.jsonl`）、header 写新 `id` 并加 `parentSession = 原文件绝对路径`；先写临时文件再 `rename` 原子落位；**原文件一个字节都不改**。

**host 编排（`piViewProvider.ts`）**

- 前置守卫（任一不满足即返回 `actionResult { ok:false, error }`，不做任何写盘）：
  - `state.isStreaming === true` → 「回合进行中，无法修改历史」
  - `state.sessionFile` 缺失（`--no-session` 临时会话）→ 「当前会话不落盘」
  - 文件不可读 / header 版本不受支持 / 任一条目校验失败 → 「不支持该会话格式」
  - `resolvePromptEntryId` 失败 → 「无法定位该消息」
- 删除：`planDeletePrompt` → 写新文件 → `switch_session` → `waitForSessionReplacement` → `refreshSnapshot`
- 编辑：`planTruncateFromPrompt` + `applyEditText` → 写新文件 → 切换 → **`prompt(newText)`**
- 重新生成：`planTruncateFromPrompt`（丢弃该用户消息及其后全部）→ 写新文件 → 切换 → **`prompt(原文)`**，由 pi 重新追加重建用户消息与新回复（PI-Desktop 的 `retryAssistantMessage` 也是走回用户消息再重放）
- 全部包在 `enqueueSessionMutation` 里，与现有 session mutation 串行。

**为什么"编辑/重生"也要截断尾部**：后续回复是针对旧文本产生的，保留会自相矛盾；这与 ChatGPT 一致，也是 PI-Desktop 的做法。

### Phase 6 — 子代理掐断（受管扩展）

- `.pi/extensions/trellis/index.ts`：
  - `trellis_subagent` 参数表新增 `timeoutSeconds`（主代理自行决定；默认 600，上限 900）。
  - `runPi()` 内记录 deadline，到点对子进程 `SIGTERM` → 宽限后 `SIGKILL`；run 状态置 `timeout`，error 文本为「Still running after Ns — truncated by timeout」。
  - 返回值附每 run 的分段结果与状态，主代理可据此决定重试哪一路。
- 风险提示：该文件在 `.trellis/.template-hashes.json` 里有哈希，属 `trellis init` 生成物，`trellis update` 时可能要求确认覆盖。将改动记入 spec，保持补丁最小、可直接上游。

## 五、风险与边界

- **会话格式耦合**：这是 B 路线的既定代价。缓解：版本号硬校验、全量校验通过才写、失败即拒绝并保持原会话、原文件永不修改。
- **文件名/header 形状**：pi 的会话发现依赖命名与 header 一致；计划沿用观测到的 `<时间戳>_<uuid>.jsonl` 形状，并用真实 pi 手工验证一次可 `--resume`。
- **序号映射脆弱**：靠文本校验兜底，不匹配就禁用而非猜测。
- **删除不可逆感知**：虽然原文保留，但会话身份会切换；用确认弹窗明示。
- **受管扩展被覆盖**：`trellis update` 时按提示保留。
- **不做**：修订历史/撤销分页（PI-Desktop 的 revision 机制）、删除后回填后续轮次、跨工作区会话。
